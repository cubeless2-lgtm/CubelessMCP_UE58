# Evidence levels and completion

Use explicit statuses: `unassessed`, `source_reviewed`, `archived`, `implemented`, `registered`, `executed`, `behavior_verified`, `blocked`. Archive is not implementation. Registration is not behavior verification. For mutation also report compile, save, reload, dependency inspection and no-MCP package/run separately.

Evidence records include source paths/hashes/commit, engine build, project, test input fingerprint, toolset/schema, stage timing, observed output, expected checks, side effects and reports. Mark absent checks `not_run`; do not convert them into passes. Choose representative success and failure cases by risk and changed behavior, prioritizing build, registration, core operations and truthful failure state. Report-tampering tests and additional independent verification need a concrete risk, prior defect or changed contract; do not duplicate equivalent evidence routinely.

Keep complete feature and pipeline tracking without requiring every verification layer for every feature. Reuse applicable evidence with its source version and scope; save/reload at meaningful persistence boundaries and group packaging at major integration or runtime-dependency changes. An untested variant remains explicitly untested even when a representative case passes.

## Support scope and verification verdicts

Keep implementation support and verification evidence separate within the existing records; these distinctions do not introduce new ledger status values. An untested type, inheritance case, container or unloaded reference is "미검증", not automatically "미지원" or "미구현". Missing evidence proves neither support nor lack of support. State the confirmed normal path and the remaining uncertainty separately; do not downgrade that confirmed path solely because other variants were not tested or promote those variants to verified.

Use "미구현" only when source inspection confirms missing work logic. Use "현재 미지원" for an evidenced implementation restriction or incompatible API condition, with the exact condition and source or observed refusal; distinguish deliberate restrictions from defects that reject valid inputs. When the cause is not established, report the observed failure and "원인 미확인" rather than inventing a support limit.

For a new failure, distinguish compile/type errors, actual engine-operation failures, verifier false rejections and intended invalid-input rejections. Confirm a verifier false rejection against the public contract, installed engine source and actual state; a failed check alone is not proof the verifier is wrong. Intended rejection is not an implementation defect. Preserve the original result and report observed changes, compile/save state and any corrected assessment separately; a later recovery or save does not make the original request successful. Never retry an uncertain mutation to resolve a reporting discrepancy.

Correct misleading current descriptions and records for the feature being handled, using existing applicable evidence. Do not reclassify all historical records, repeat completed verification or rewrite APIs solely because evidence is absent. Repair code only for a confirmed defect or an explicitly requested support expansion. Retain real implementation gaps and safety checks; verification terminology changes do not relax completion requirements.

## Required plugins and conditional availability

Apply this rule across all API families, pipelines, reviews, completion summaries and user-facing reports. An API that uses another plugin is available under that plugin's supported, enabled and loaded configuration. Record the required plugin names and relevant engine/version or restart conditions with the feature. If a prerequisite is disabled, report "필수 플러그인 활성화 필요"; do not count that condition as a defect, failed migration or unsupported implementation. Do not report a successful execution when only activation or registration was checked.

When the intended operation succeeds with its prerequisites enabled and the applicable checks pass, report "정상 동작 확인 — 필수 플러그인: …" and mark the verified scope complete/usable. Dependencies alone are not unfinished work. Existing evidence can support this verdict without repeating successful tests. Preserve genuinely unimplemented variants, incompatible versions, failed activation/loading and actual execution failures as separate issues. Enable only the dependencies needed for the chosen feature, not all optional plugins in every project.

Required standard engine/runtime plugins are legitimate output dependencies. Descriptor/config entries, receipt names or confirmed inert registration code do not by themselves prove a forbidden runtime dependency. Determine actual module type, build configuration, object references and behavior before classifying them. The prohibition on game dependencies on Cubeless, official MCP/Toolset development functionality and editor-only execution still applies; merely enabling those plugins does not satisfy it.

Retain raw results from older zero-metadata checks as historical diagnostics. Once the presence is established as a normal prerequisite or harmless metadata within the verified scope, do not continue presenting it as a current blocker or unresolved functional defect. Record the current conditional verdict and its supporting evidence separately; never erase the original failure or turn an unexecuted operation into a success. Apply this prospectively and to the feature currently being handled, without a blanket reclassification of unreviewed history.

Legacy ledger final dispositions are: (1) Cubeless implemented+registered+required verified behavior; (2) official tool proven equivalent in IO/defaults/errors/side effects/verification; (3) old transport-only functionality removed with evidence; (4) incomplete. Planned disposition is distinct from final disposition. File counts, routes, Python definitions and pipeline candidates overlap and must not be added as unique feature totals.

Record performance with call count, compile/save count, workload and wall time. Source LOC and person-hour estimates are not measured engine performance. Past UE5.6 evidence stays labeled UE5.6 until independently rerun in UE5.8.

Identify binaries by source-bundle inventory, engine build, DLL hash and an existing artifact location. Reuse those references across checks instead of making a DLL/PDB backup for every verification. Keep the active projects' required binaries/symbols, one verified latest recovery build and any distinct failure artifact needed for reproduction. Remove only stopped, owned, demonstrably regenerable or redundant outputs; preserve source/config/assets and raw success/failure records.

Current baseline summaries must be built from explicit current fields. Do not spread an older baseline record into a new one while replacing only `files`/`count`: old `protected_original_count`, `total_count`, owned-asset maps and source receipts can remain misleading. Keep previous summaries under a named historical object, preserve the original record, and correct metadata through a successor without repeating Engine behavior.
