# Runtime independence verification

Cubeless editor C++ and the official MCP runtime modules must not become a game dependency. An Editor module descriptor alone is insufficient proof.

Keep the standard engine/runtime plugins required by the content enabled, including Niagara or GeometryCollectionPlugin when those features are used. Runtime independence means independence from MCP authoring/development functionality, not removal of legitimate engine feature dependencies. Apply the [conditional availability rule](../policies/evidence.md#required-plugins-and-conditional-availability): successful behavior under documented prerequisites is complete within its verified scope. Metadata-only findings from a stricter historical checker remain diagnostic evidence, not functional blockers once their actual role is established. Do not globally whitelist all engine plugins or ignore real editor-code/runtime reference failures.

Inspect plugin descriptor dependencies, project references, build dependencies, generated asset parents/nodes/class paths and hard/soft/management package references. Forbidden output references include the actual Cubeless script module and mount names, not just a substring search.

Use this development and verification project to test with Cubeless and official MCP/Toolset development plugins disabled, using a safe per-run configuration where available and preserving the user's active Editor and configuration. Load the generated fixture and compile it. If the required disabled-plugin state cannot safely be established here, report the limitation; do not create or use a separate project, project copy or temporary host project unless the user explicitly directs otherwise, and do not claim this gate passed without the disabled-plugin test. Build/cook/stage the game for the target platform within the requested verification scope and inspect module receipts and staged files. Run the output in the corresponding target environment without the MCP plugin/server and verify intended behavior. Win64 is one platform-specific case, not a substitute for other target-platform verification; record unavailable build/run checks as `not_run`. Record unrelated preexisting package errors separately. Do not add a gameplay C++ module merely to bypass a plugin build issue.

Run this gate at major integration milestones or when runtime-dependency structure changes, using representative fixtures for the affected risks. Do not repeat packaging after every feature or rerun equivalent proof without a relevant change or failure. Reuse applicable prior evidence with its source/version and coverage limits; new or untested behavior remains explicitly unverified. Missing package/run proof remains `not_run` even if asset-level reference inspection passes.
