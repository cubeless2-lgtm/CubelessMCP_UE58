# CubelessMCP_UE58 UE 5.8.3 작업량 견적

2026년 10월 10일의 소스 조사에 근거한 **낮은 신뢰도의 조건부 규모 견적**이다. 범위는 [이식 계획](UE58_MIGRATION_PLAN.md)의 전체 기능 보존, 파이프라인·검수 Python의 독립 이식, 실제 UE 5.8.3 검증 및 MCP 없는 Win64 패키징이다.

아래 단위는 숙련 개발자가 수행할 때의 **인시(person-hour)**다. Codex가 이 시간 동안 실행되어야 한다는 뜻도, 청구 금액이나 확정 납기도 아니다. 기존 코드를 재사용하고 자동화할 수 있지만 실제 이식 속도를 측정하지 않았으므로 임의의 AI 가속 배율을 적용하지 않는다. 확정된 API 대응과 독립 파이프라인 수가 부족해 전체 고정가·고정 기간을 약속할 단계는 아니다.

## 요약 견적

| --- | ---: | ---: | ---: |

대외적인 규모 표현은 **약 1,200 / 2,500 / 4,800 인시**다. 숫자의 자릿수가 정밀도를 의미하지 않으며 각 작업 묶음의 추정치를 더한 결과다. 고난도 값도 상한 보장이나 기술적으로 불가능한 항목의 해결 약속이 아니다. 미조사 기능이나 복구 불가능한 입력이 드러나면 다시 산정한다.

이것은 사람 기준의 프로젝트 규모다. 한 명이 주 40시간을 온전히 투입한다고 단순 환산하면 각각 28.9 / 61.4 / 120.4 인주지만 실제 팀 일정이나 Codex 완료 일정으로 사용하지 않는다. 조사·작성·리뷰는 병렬화할 수 있고 에디터 수정, 공유 fixture, 빌드·종단 검증에는 직렬 단계가 있다.

**권장 착수 단위는 전체 중 40~80인시 상당의 초기 실측 구간**이다. 아래의 작은 구간을 먼저 실제로 수행한 뒤 Codex 작업시간, 엔진 대기, 재작업을 나누어 잔여 견적을 다시 계산한다. 이 40~80은 전체 견적에 포함되며 추가 비용으로 더하지 않는다.

줄 수는 전부 다시 작성할 양이 아니다. 기존 코드의 재사용률도 아직 측정하지 않았다. 3,518개는 Docs까지 포함한 운영 자료 집합의 수이며 이전 6개 루트에서 잡힌 3,382개 경로와 조사 범위가 다르다. 아직 전수 조사에서 추가될 경로가 있다.

이름 기반 pipeline 후보 1,131개와 verifier 후보 1,491개에는 284개 중복이 있고, 두 이름 tag가 모두 없는 스크립트도 1,180개다. 따라서 이름 검색 결과를 독립 파이프라인 수로 사용하지 않는다. 실제 산정 단위는 `원본 entrypoint/phase → 공통 흐름 → 유일한 입력·단계·검수 차이 → 5.8 실행 증거`다.

내용이 완전히 같은 중복이 적다는 사실도 의미상 중복이 적다는 뜻은 아니다. 예제·일회성 실험을 공통 recipe와 fixture로 묶을 수 있지만, 각 원본의 고유 기능과 판정 기준 연결을 남겨야 한다. 파일을 archive하거나 범용 실행 도구로 호출할 수 있게 만드는 것만으로 완료를 인정하지 않는다.

## 세 가지 시나리오의 가정

- **낙관:** 기존 기능 로직과 fixture를 상당 부분 재사용하고 공개 API 차이가 제한적이다. 대형 스크립트군의 의미상 중복이 높아 공통 흐름과 입력 변형으로 표현할 수 있다. 기능·검수를 생략하는 가정은 없다.
- **기준:** 일부 엔진 API, graph/pin 구조, compile/save 동작, 외부·내부 Python 경계를 수정해야 한다. 하드코딩된 에셋·GUID를 parameter화하고 실패 보고·fixture를 보강한다.
- **고난도:** Niagara Internal, RigVM/AnimGraph, Chaos 등에서 다수 재설계가 필요하고 과거 fixture·에셋 상태를 재구성해야 한다. GPU·PIE·재로드 문제가 반복된다. 그래도 엔진 소스 수정과 런타임 C++ 의존성은 허용하지 않는다.

세 시나리오 모두 Win64·UE 5.8.3만 검증하며, 필수 엔진·도구·에셋·제3자 의존성을 기존 권한과 라이선스로 사용할 수 있다는 조건이다. 신규 구매, 외부 서비스 사용료, 추가 플랫폼, 제품 기능 추가, 게임플레이 C++ 개발, 장기 호스팅 운영은 포함하지 않는다. 이 전제가 틀리면 비용을 임의 집행하지 않고 장애와 대안을 제시한다.

공식 도구로 동등하게 대체되는 비율이 높으면 구현량은 줄 수 있지만 계약 비교와 실제 실행 검증은 남는다. 반대로 공개 API로 구현할 수 없는 항목은 시간을 더 썼다는 이유로 완료로 바꾸지 않는다.

## 현재 줄어든 불확실성과 남은 위험

- **확인됨:** 설치본 UE 5.8.3 CL 58210709, 공식 C++·Python Registry 확장 코드, 공식 Toolset 52개 목록, 스키마 조회와 읽기 호출. 최신 조회에서는 과거 승인 정책 오류가 재현되지 않았다.
- **설치만 확인:** Visual Studio 18 Community VC 도구 14.51.36231, Windows SDK include 디렉터리 10.0.22621.0 및 10.0.26100.0. 실제 UBT 호환성과 플러그인 빌드 성공은 미검증이다.
- **미확정:** 독립 PIPE/VERIFY 수, 실제 코드 재사용률, 5.6 격리 비교 실행, 전체 공식 대체율, 과거 fixture·서비스 의존성, 비공개 엔진 API 대안, 기존 프로젝트 패키징 오류의 영향.
- **확정 제약:** 원본·엔진 소스 수정 금지, 게임 런타임 의존성 금지, 사용자 에셋 보존, 모든 고유 기능 추적, 실제 파이프라인·검수 실행. 견적을 낮추기 위해 이 조건을 생략하지 않는다.

## 실측 후 견적 보정 방법

1. 초기 구간의 실제 agent 작업 시간, 빌드·shader·cook 대기, 에디터 검증 시간, 재작업, 사용자·외부 의존 대기를 각각 기록한다.
2. 전수 후보를 확정된 기능·PIPE·VERIFY와 공통군·유일 차이로 묶고, 각 원본 ID가 남아 있는지 대조한다.
3. 서로 다른 도메인의 3~5개 흐름을 실제 5.8에서 끝까지 실행하여 단순·복합·고위험 항목의 실측 단가를 구한다. 예제 하나의 속도를 모든 항목에 적용하지 않는다.
4. `완료 실측 + 유형별 잔여 수 × 유형별 실측 단가 + 공통 통합 작업 + 식별된 위험`으로 잔여 견적을 갱신한다. 병렬 가능한 부분과 에디터 직렬 경로를 구분한다.
5. 구현이 어려운 기능은 대장에서 제거하지 않는다. 예정 대응 변경·새 장애·변경된 견적 근거를 기록하며 필수 미완료가 남으면 전체 완료로 선언하지 않는다.

금액 견적은 수행 주체와 단가가 정해져야 계산할 수 있다. 현재 문서에는 임의의 원화 단가나 Codex/API 사용료를 넣지 않았다. 유료 인력 견적은 합의한 시간당 단가에 인시를 적용하고, Codex 사용량은 실제 실행의 토큰·플랜·과금 조건으로 별도 계산해야 한다.
