# CubelessMCP_UE58 UE 5.8.3 이식 계획

2026년 10월 10일 확정한 계획이다. 목표는 UE 5.6에서 추가한 MCP 기능, 복합 파이프라인, 검수 Python과 운영 경험을 빠짐없이 추적하여 UE 5.8.3의 공식 MCP 확장 구조로 이전하는 것이다. 같은 날 사용자가 구현 착수를 승인했다. 아래 조사 기준선은 계획 당시의 기록이며 현재 구현·검증 상태는 [구현 대장](implementation-2026-10-10/migration-ledger.json)과 작업 기록에서 관리한다. 커밋·푸시는 별도 요청 전까지 수행하지 않는다.

현재 실행 계획과 완료 기준은 이 문서를 기준으로 한다. [작업량 견적](UE58_MIGRATION_ESTIMATE.md)은 별도로 관리하며, 상세 기능 대응과 초기 구현 실측에서 갱신한다. 최초 빌드·패키징 검증 플랫폼은 현재 작업 환경인 Win64로 한정한다. 다른 플랫폼 검증은 별도 산정한다.

최신 사용자 방향에 따라 플러그인의 빌드·공식 등록·핵심 작업·실패 상태를 우선하고 위험 기반 대표 검증을 수행한다. 기능·파이프라인은 전수 추적하되, 공통 코어를 쓰는 모든 파일에 같은 fixture와 종단 검증을 반복하지 않는다. 공통 계약의 실행 증거와 적용 범위를 연결하고 고유 계약 차이·고위험 실패를 선택해 확인한다. 저장·재로드는 의미 있는 영속성 경계에서, 패키징은 주요 통합이나 런타임 의존성 구조 변경 시 묶어서 수행한다. 미검증 범위를 통과로 표시하거나 대표 경로의 성공을 전체 기능 완료로 확대하지 않는다.

사용자가 지정한 대상 원격 저장소는 [cubeless2-lgtm/CubelessMCP_UE58](https://github.com/cubeless2-lgtm/CubelessMCP_UE58)다. 2026년 10월 10일 읽기 조회에서 빈 저장소임을 확인했다. 이 주소는 이식 결과의 저장소 지정이며, 현재 로컬 Git 초기화·remote 연결·커밋·푸시를 수행한 상태는 아니다. 기존 프로젝트 루트와 폴더 배치는 유지하고, 실제 Git 추적 범위와 생성물 제외 규칙은 저장소 구성 단계에서 정한다. 커밋·푸시는 사용자의 별도 요청 전까지 수행하지 않는다.

## 확정 요구사항

1. 원본 `C:/Git/UnrealMCP5_6_1`은 수정하지 않는다. HEAD뿐 아니라 미커밋·스테이징·미추적 상태의 추가 기능도 조사한다.
2. 대상 프로젝트 루트는 `C:/Git/UnrealMCP5_8_3/UnrealMCP5_8_3`이다. 기존 사용자 콘텐츠, 설정, Python 시작 스크립트와 상위 `RetargetTools`의 작업·백업을 보존한다.
3. 공개 Python 도구, 내부 명령, C++ 핸들러, 반영된 UFUNCTION, 배치, 파이프라인, 검수, 보조 스크립트를 모두 추적한다. 검색 화면이나 문서의 도구 수만으로 범위를 제한하지 않는다.
4. 5.8에서 API·타입·기본값·실행 조건·저장 및 컴파일 동작이 바뀌었다면 실제 설치본과 실행으로 확인하고 고친다. 어려운 기능도 목록에서 제외하지 않는다.
5. `Codex → 공식 ModelContextProtocol → 공식 Toolset Registry → CubelessMCP_UE58 → UE API` 경로를 사용한다. 별도 MCP 서버, 자체 TCP 브릿지, 엔진 플러그인 소스 수정은 도입하지 않는다.
6. 게임 런타임에 CubelessMCP_UE58 C++ 의존성을 남기지 않는다. 게임 모듈이 CubelessMCP_UE58를 참조하거나 CubelessMCP_UE58가 특정 게임 C++ 모듈에 직접 의존하는 구조를 금지한다.
7. 플러그인의 에디터 작업을 위한 C++는 사용한다. 공식 등록, Python에 노출되지 않은 공개 API 래퍼, 비동기 처리, 성능이 중요한 배치와 검증을 담당하게 한다. Python만으로 제한하지 않는다.
8. 생성한 게임 에셋·블루프린트에도 CubelessMCP_UE58 클래스, 부모 클래스, 컴포넌트, 구조체, 함수 노드, 경로의 영속 의존성을 남기지 않는다. 플러그인을 제거해도 생성 결과가 독립적으로 동작해야 한다.
9. 기존 MCP 파이프라인과 검수 Python은 독립된 이식 대상이다. 복사·보관, 문법 검사, 개별 도구 성공만으로 파이프라인 이식 완료라고 판정하지 않는다.
10. 실제 UE 5.8.3에서 공식 연결의 검색·호출, 필요한 컴파일·저장·재로드, 파이프라인 실행, 패키징 의존성을 검증한다. 미완료 또는 필수 미검증이 남으면 전체 이식 완료로 선언하지 않는다.

## 누락을 막는 기능 대장

도구 이름을 유지하는 것과 기능을 유지하는 것을 구분한다. 하나의 기존 도구가 여러 독립 작업을 제공하면 작업별 계약을 추가하고, 여러 도구가 같은 내부 작업을 사용하면 연결 관계를 유지한다. 내부 도구·명령을 통합하더라도 모든 원본 항목이 대상 구현·대체 근거·제거 근거·미완료 사유 중 하나에 연결되어야 한다.

각 항목에 다음 정보를 둔다.

- 안정적인 ID, 기능군, 원본 파일·줄·해시·Git 버전, 현재 작업트리와의 차이.
- Python 공개 도구와 등록 조건, 내부 명령·별칭, C++ 핸들러, 호출한 엔진 API, 반영 API 및 직접 스크립트 호출 관계.
- 입력·출력 스키마, 기본값, 허용 값, 오류·부분 성공, 부작용, 컴파일·저장·트랜잭션 경계.
- 호출하는 파이프라인과 검수기 ID, 실행 위치, 필요한 플러그인과 에셋 유형.
- UE 5.8 변경점, 조사 근거, 대상 Cubeless Toolset 및 함수, 대상 엔진 API.
- 아래 최종 분류, 구현 상태, 검증 상태, 증거 파일, 남은 문제와 다음 조치.

상세 계획의 `planned_disposition`과 실행 증거가 있는 `final_disposition`을 분리한다. P3에서 구현·대체 예정 경로를 정할 수 있지만, 구현 전 항목을 분류 1·2의 완료로 기록하지 않는다. 공식 대체 후보는 원본과의 계약·실행 비교가 통과한 뒤 최종 분류 2가 된다.

| 최종 분류 | 적용 기준 |
| --- | --- |
| 1 CubelessMCP_UE58 구현·등록 | 기존 동작을 구현하고 공식 Registry와 MCP에서 제공. 복합 작업은 배치 및 검수 흐름까지 유지 |
| 2 공식 5.8 도구로 동등 대체 | 입력·출력·기본값·오류·부작용·검증 수준을 대조하고 실행 증거 확보. 필요한 파이프라인도 함께 수정·검증 |
| 3 기존 통신 구조 전용 기능 제거 | 외부 서버 시작·자체 TCP framing·포트 관리 등 통신 전용임을 입증. 그 안의 검증·배치·오류 처리 로직은 분리해 유지 |
| 4 미완료 | API 차이, 비공개 API, 미지원·미검증·환경 장애 등으로 요구 동작을 달성하지 못한 항목. 사유와 대안 및 재개 조건 기록 |

현재 정적 후보 목록은 `unassessed` 상태다. 이것은 계획 조사 상태이며 위 네 가지 최종 분류를 대신하지 않는다. 기능 보존을 기본 방향으로 두고, 상세 조사와 비교가 끝난 항목부터 최종 분류를 확정한다. 공식 도구의 이름이 비슷하거나 범용 Python 실행이 가능하다는 이유만으로 2번을 부여하지 않는다. 완료 보고 시 미분류는 0이어야 한다.

누락 대조는 `Python 소스 ↔ 소스 등록 구성 ↔ 런타임 검색·등록 전체 목록 ↔ 내부 명령 ↔ C++/반영 API ↔ 파이프라인·검수 호출`의 양방향 차집합으로 수행한다. 기본 compact/search 모드가 숨기는 도구와 별칭, 직접 UFUNCTION 호출도 포함한다. 원본을 실행해야 하면 격리된 복사본에서만 수행한다.

## 플러그인 구조와 C++ 경계

사용자가 지정한 플러그인 이름은 저장소와 동일한 `CubelessMCP_UE58`이다. 폴더·descriptor 파일과 표시 이름에 이 이름을 사용한다. 에디터 C++ 모듈은 `CubelessMCPUE58Editor`, Python 패키지는 `cubeless_mcp_ue58`로 계획하며, MCP 도구의 충돌 방지 접두사는 `Cubeless`를 유지한다. 아래 `Content/Python`은 플러그인 내부의 에디터 Python 코드 위치이고 프로젝트 게임 콘텐츠 폴더와 별개다. 이 명명은 계획에 반영한 것이며 아직 실제 빌드·등록으로 검증한 구현은 아니다.

파일 배치는 계획이며 아직 위 플러그인과 운영 지침을 생성하지 않았다. 처음에는 에디터 전용 C++ 모듈 하나를 사용하고 실제 의존성 분리가 필요할 때만 세분화한다. UE 5.6·5.7·가상 미래 버전을 지원하는 추상 계층은 미리 만들지 않는다.

등록부는 도구 노출과 입력·출력 변환을 맡고, 작업 로직은 등록 API를 직접 호출하지 않는다. 작업 로직의 버전 의존 엔진 호출을 UE58 호환부에 모은다. Python Toolset과 C++ Toolset 모두 구체적인 기능별 인터페이스를 제공하고, 실제 Registry 이름 규칙에 맞는 충돌 없는 `Cubeless` 접두사를 사용한다.

설치 소스에서 `UToolsetDefinition`, `UToolsetRegistry::RegisterToolsetClass`, C++ `AICallable`, Python `toolset_registry.tool_call` 경로를 조사한다. 구현은 [엔진 등록 조사](planning-2026-10-10/ue58-registration-findings.md)의 실제 서명과 생명주기를 기준으로 한다. 공식 안내 역시 Registry 확장을 권장한다. [Epic Unreal MCP 문서](https://dev.epicgames.com/documentation/unreal-engine/unreal-mcp-in-unreal-editor?application_version=5.8)

### Python 경로와 초기화

최종 선택은 `<project>/Plugins/CubelessMCP_UE58/Content/Python/cubeless_mcp_ue58/`다. UE가 활성화된 플러그인의 `Content/Python`을 검색 경로에 넣고 `init_unreal.py`를 실행하는 공식 관례를 따른다. 프로젝트의 게임 콘텐츠 폴더와 플러그인 내부 Content를 구분한다. [Epic Python 경로 문서](https://dev.epicgames.com/documentation/ko-kr/unreal-engine/scripting-the-unreal-editor-using-python)

1. 플러그인의 `Content/Python/init_unreal.py`는 패키지 import와 등록만 수행하는 얇은 진입점으로 둔다. 실제 작업 로직을 넣지 않는다.
2. Python 등록부는 공식 Registry 가용성·패키지 버전·중복 등록을 검사한다. import 성공과 등록·스키마·MCP 노출 성공을 구분한다.
3. C++ 에디터 모듈은 C++ Toolset 등록, 공개 API 래퍼, 비동기 작업 관리와 필요한 종료 생명주기를 담당한다. Python 경로 때문에 별도의 C++ bootstrap을 만들지 않는다.
4. 종료 시 Python·Registry가 유효한 순서에 맞춰 등록·delegate·작업 상태를 정리한다. 플러그인이 비활성화된 새 세션에서는 Cubeless 도구가 노출되지 않아야 한다. 도구 작업 중 모듈 unload를 안전하다고 가정하지 않는다.
5. 운영체제 `PYTHONPATH`·`UE_PYTHONPATH`, 프로젝트 전역 Additional Paths/Startup Scripts, 사용자 프로젝트의 기존 시작 스크립트 변경을 기본 설치 조건으로 요구하지 않는다.

근거는 `Engine/Plugins/Experimental/Toolsets/EditorToolset/Content/Python/init_unreal.py`와 `Engine/Plugins/Experimental/PythonScriptPlugin/Source/PythonScriptPlugin/Private/PythonScriptPlugin.cpp:1682,2063`이다. 실제 CubelessMCP_UE58의 시작·종료·검색·호출은 P1에서 검증한다. 자동 검색 위치에 파일을 둔 사실만으로 Toolset 등록 완료라고 판단하지 않는다.

플러그인 기능 제공에 필요한 C++와 에디터 Python을 **`Plugins/CubelessMCP_UE58` 안에 함께 배포**한다. `cubeless/tools`의 외부 파이프라인·검수기와 운영 자료는 별도 개발 도구이며, 플러그인의 정상 로드·등록·도구 호출에 필수인 구현을 그쪽에 숨겨 두지 않는다. 외부 검수와 전체 운영 재현 시에는 해당 도구·설정·fixture·버전 manifest도 함께 제공한다.

P1에는 경로의 공백·한글, 다른 위치로 플러그인 복사, 새 세션의 자동 등록, 재등록·해제, 패키지 누락, 기존 리타기팅 초기화 보존을 포함한다. cook/stage 결과에서 Python 소스와 MCP 플러그인의 제외를 확인한다. 폴더 위치만으로 런타임 독립성이 증명된다고 보지 않는다.

### 런타임 의존성 금지 검증

- CubelessMCP_UE58 C++ 모듈을 에디터 전용으로 선언한다. Runtime 또는 RuntimeNoCommandlet 모듈을 추가하지 않는다.
- 게임 `Build.cs`, Target, 게임플레이 코드에 CubelessMCP_UE58 의존성을 추가하지 않는다. CubelessMCP_UE58도 게임 모듈명을 빌드 의존성에 넣지 않는다.
- 게임 결과는 엔진 기본 타입 또는 명시적으로 허용된 기존 게임 타입으로 만든다. CubelessMCP_UE58의 클래스·USTRUCT·UENUM·함수·컴포넌트를 런타임 결과에 저장하지 않는다.
- 패키지의 hard/soft/관리 의존성, 블루프린트 부모 및 함수 노드, object/class 경로를 검사하고 `/Script/CubelessMCPUE58Editor`와 `/CubelessMCP_UE58/` 등 실제 모듈·마운트 경로를 금지 목록에 반영한다. 단순 문자열 검색만으로 검증을 끝내지 않는다.
- 공식 `ModelContextProtocol`에도 Runtime 모듈이 있으므로 CubelessMCP_UE58만 Editor로 선언해서 끝내지 않는다. 프로젝트에서 공식 MCP·Toolset 관련 플러그인 참조와 전이 의존성을 조사하고, 엔진 소스를 수정하지 않는 Editor 대상 활성화 방식으로 제한한다.
- 생성 에셋을 저장·재로드한 뒤 격리 검증 사본에서 CubelessMCP_UE58 및 MCP 관련 플러그인을 비활성화해 로드·컴파일한다. Game/Shipping 빌드·cook·stage 결과와 module receipt·포함 파일·실행 로그를 대조한다. MCP 없이 결과물을 실행한다.
- 기존 5.6 기능이 플러그인의 런타임 클래스를 필요로 한다면 동일 기능을 독립 결과로 생성하는 방식으로 재설계한다. 불가능하면 기능을 삭제하거나 C++ 제약을 완화하지 않고 분류 4로 보고한다.

## 파이프라인과 검수 Python의 독립 이식

개별 도구 대장과 별도로 `PIPE`와 `VERIFY` ID를 부여한다. 파일 하나와 파이프라인 하나가 반드시 일치하지는 않는다. 여러 스크립트의 순서, 생성 스크립트, 공유 helper, fixtures와 보고서 후처리까지 연결한다. 게임 콘텐츠를 생성하는 예제와 MCP 자체 기능 검수도 구분해 둘 다 조사 범위에 남긴다.

각 파이프라인·검수 항목의 계약에는 다음을 기록한다.

| 기록할 내용 | 세부 항목 |
| --- | --- |
| 실행 위치 | 에디터 내부 Python / 외부 Python / 두 환경에 걸친 orchestration. interpreter·모듈·플러그인·시작 방법 |
| 입력 | CLI·환경 변수·설정·manifest·테스트 에셋·전제 상태·기본값·스키마 |
| 호출 흐름 | preflight → 검색 → 조회 → 생성/수정 → 컴파일 → 저장 → 검수 → 재로드 → 보고. 실제 원본 순서·분기·반복·배치 단위 기록 |
| 대상 대응 | 각 단계의 기존 도구·내부 명령·엔진 API와 5.8 Toolset/API 연결. 도구 변경으로 달라지는 결과 parsing도 수정 |
| 출력 | 에셋, 파일, 상태, 중간 결과, 콘솔·JSON·Markdown·이미지 등 보고서와 경로·스키마 |
| 검수 기준 | 기대값·관측값·허용 오차·불변조건·전체/부분 성공·시각 검수 필요 여부 |
| 실패 처리 | 실패 단계, 이미 변경된 에셋, 컴파일·저장 상태, 부분 보고서, 종료 코드, 타임아웃·취소·연결 종료 |
| 재실행 | idempotency 여부, checkpoint·resume 조건, 중복 생성·덮어쓰기 위험, 정리·복구 범위 |
| 증거 | 원본 기준 실행 또는 소스 기반 계약, 5.8 실행 조건·로그·보고서, 에셋 재로드, 비교 결과 |

외부 Python은 공식 MCP에 접속하는 클라이언트 또는 검수·보고서 도구로 유지할 수 있다. 기존 외부 Python MCP 서버와 TCP 브릿지를 실행하는 방식은 새 구조의 필수 의존성으로 남기지 않는다. 에디터 내부 Python은 `Plugins/CubelessMCP_UE58/Content/Python/cubeless_mcp_ue58/`에, 외부 진입점은 `cubeless/tools/`에 두어 실행 환경을 구분한다. 외부 코드에서 `unreal` 모듈을 직접 사용할 수 있다고 가정하지 않는다.

파이프라인 완료 조건은 다음을 모두 충족하는 것이다.

1. 원본 단계·입출력·판정·실패 계약을 조사하고 대상 도구에 맞게 수정했다.
2. 실제 UE 5.8.3에서 격리된 테스트 에셋으로 처음부터 마지막 보고서까지 실행했다.
3. 기대 결과와 검수 결과가 일치하며, 필요한 컴파일·저장·새 프로세스 재로드까지 확인했다.
4. 적절한 실패 입력·중간 실패·중복 재실행 사례에서 상태와 보고서가 실제 변경과 일치한다.
5. 보고서 파일의 생성 여부뿐 아니라 스키마·누락 항목·실패 전파·증거 링크가 맞다. 보고서 자체 반례 시험과 중복 독립검수는 구체적인 위험·기존 결함·계약 변경의 근거가 있을 때 추가한다.
6. 단계별 호출 수, 실행 시간, 컴파일·저장 횟수와 비동기 대기 시간을 기록했다.

`archived`, `copied`, `ported`, `executed`, `behavior_verified`를 구분한다. 이식 완료는 필수 검증을 마친 상태에만 부여한다. 외부 도구가 종료 코드 0을 반환하거나 MCP가 정상 응답했다는 사실만으로 엔진 작업 성공을 판단하지 않는다.

P0의 초기 전수 후보 목록 이후 P1을 먼저 확인하고 P3의 상세 분석을 이어간다. 특정 기능의 5.8 대응 조사와 구현은 작은 단위로 반복한다. 모든 API를 미리 추측한 뒤 한 번에 빌드하는 방식은 사용하지 않는다. 단계 완료는 전체 이전 완료와 다르다.

### 초기 실측 구간과 단계별 판단

처음에는 P0·P2의 일부와 P1을 묶어 공식 C++/Python 등록, 실제 빌드, 최소 에셋의 저장·재로드와 MCP 없는 패키징, 고위험 엔진 API 표본 및 독립 파이프라인 하나를 확인한다. 이 구간을 통과해도 전수 조사·전체 이식 완료가 아니다. 실제 소요와 장애를 기록하여 견적을 보정한다.

기능군은 작업 ID와 허용 변경 경로를 배정하고, 파일 조사·독립 코드 작성·검토를 병렬화한다. 에디터 수정·컴파일·저장·PIE와 연결 설정 변경은 한 실행 담당자가 직렬로 수행한다. 검수 담당은 구현 결과를 그대로 믿지 않고 독립 readback·실패 fixture·재로드·보고서 일관성으로 확인한다.

현재 프로젝트에는 gameplay Source 모듈이 없다. 에디터 플러그인의 공식 빌드 경로를 먼저 확인하고, 빌드를 편하게 하려고 게임 런타임 C++ 모듈이나 플러그인 하드 의존성을 만들지 않는다. 엔진·프로젝트·fixture·외부 의존성 버전과 빌드 명령을 각 실행 보고서에 남긴다.

구현 단계가 시작되면 범위 안의 일반 작업에는 단계마다 반복 승인을 요구하지 않는다. 기능 축소, 원본·엔진 소스 변경, 런타임 의존 허용, 사용자 미저장 작업의 처리처럼 현재 범위를 바꾸는 판단만 사용자에게 요청한다. 필수 API·fixture 부재는 해당 기능을 미완료로 남기고 독립된 다른 작업은 진행한다.

## 성능과 실패 처리

- UE 에셋 변경은 게임 스레드 규칙에 따라 직렬화한다. 병렬 agent는 파일 조사·독립 코드·검토를 나눌 수 있지만 에디터 변경은 한 담당자가 실행한다.
- 하나의 사용자 작업을 배치로 묶고 변경 계획을 먼저 검증한다. 가능한 범위에서 컴파일·저장을 변경 단위의 끝으로 모으되 원본의 검증 계약을 약화하지 않는다.
- Python `async def`나 워커 스레드를 붙이면 엔진 작업이 안전해진다고 가정하지 않는다. 공식 비동기 결과 API와 해당 엔진 작업의 실제 지원 범위를 먼저 확인한다.
- 긴 작업은 작업 ID, 단계, 완료·실패·취소·불확실 상태, 진행·최종 결과 조회를 설계한다. 타임아웃이 엔진 작업 취소를 뜻하는지 확인한다. 지원하지 않는 취소는 지원한다고 표기하지 않는다.
- 설치 소스의 Registry adapter와 `call_tool`에는 실제 작업을 중단하는 `CancelAsync` override가 확인되지 않았다. MCP 요청 취소와 별도로 작업 상태 및 가능한 협력 취소를 설계하고 실제 5.8에서 확인한다.
- 결과에 실패 단계, 실제 변경 목록, 컴파일·저장·검수 상태, 재실행 가능 조건과 중복 위험을 포함한다. 결과가 불확실한 수정 작업은 자동 재시도하지 않는다.
- 트랜잭션 범위와 디스크 저장·외부 파일 부작용을 구분한다. 원자적 롤백을 검증하지 못한 기능에 전체 롤백 보장을 표시하지 않는다.
- 성능은 같은 fixture·에셋 수·배치 크기·엔진 빌드·장비·캐시 조건에서 반복 측정한다. 전체 시간, 엔진 작업 시간, 호출 수, payload 크기, 컴파일·저장 횟수와 UI 응답 영향을 기록한다. 비교 가능한 5.6 실행이 없으면 5.8 측정만 보고하며 개선율을 만들지 않는다.

## 테스트 자산과 완료 판정

전용 `/Game/CubelessMCPTests/<run_id>/`와 `cubeless/records/verification/<run_id>/`를 사용한다. 기존 레벨·리타기팅 결과·사용자 작업 에셋에서 검증용 수정을 하지 않는다. 플러그인 해제 및 패키징 검증은 필요한 에셋만 포함한 격리 사본 또는 승인된 별도 검증 프로젝트에서 수행한다.

선택한 대표 경로에서 조회 기능의 값·필터·오류, 수정 기능의 실제 변경 결과, 파이프라인의 단계와 보고서를 검증한다. 컴파일·저장·재로드와 독립 검수는 변경된 계약과 영속성 위험에 맞춰 수행하고 적용 가능한 기존 증거를 재사용한다. 기존 엔진·프로젝트 오류가 검증을 막으면 원래의 오류와 새 결함을 분리해 기록하고 해당 검증은 미완료로 둔다.

검증 상태는 `not_run / passed / failed / blocked / not_applicable`로 구분한다. `registered`, `call_succeeded`는 일부 증거일 뿐 최종 완료가 아니다. 테스트 에셋 정리도 생성 manifest를 기준으로 하며 사용자 에셋을 경로 추측으로 삭제하지 않는다.

전체 완료를 선언하려면 전수 목록에 미분류가 없고, 유지할 기능과 모든 파이프라인·검수의 필수 검증이 통과해야 한다. 분류 4 또는 필수 미검증이 하나라도 남으면 남은 목록·원인·대안·재개 조건을 최종 보고에 포함한다.

## 운영 기록과 경험 보존

원본의 `codex`뿐 아니라 루트 지침, `Docs`, `Python/scripts`, `scripts`, `Tools`, `.github`, 플러그인 문서·검증 코드, `SourceArt`, `output`, `work`, 관련 임시·증거 경로를 조사한다. 모든 파일을 같은 수준의 현재 기능으로 간주하지 않고 출처와 역할을 분류한다. 읽기 불가·손상·ignore·대용량 제외 범위를 기록해 조용히 누락하지 않는다.

과거 문서는 `archive/ue56`에 원본 상대 경로와 파일 해시를 유지해 보존한다. 손상된 현재 파일과 HEAD·index·이전 커밋에서 복구한 텍스트는 별도 파일로 보관하고 원본 경로·복구 revision·복구 한계를 manifest에 기록한다. Git 버전으로 미커밋 최신 내용을 복구했다고 주장하지 않는다.

현재 운영 지침은 5.8 구조와 본 요청을 기준으로 새로 작성한다. 오래된 포트·엔진 경로·외부 저장소·에이전트 이름을 그대로 활성화하지 않는다. 경험별로 원인, 해결, 적용 조건, 검증 엔진, 근거, 현재 재검증 상태를 나눈다. 파일에 없는 대화 기억을 이전했다고 주장하지 않는다.
