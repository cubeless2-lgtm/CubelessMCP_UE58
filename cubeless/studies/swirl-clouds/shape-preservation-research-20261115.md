# 파노라마 형태를 유지하는 볼륨 구름: 기술 조사

조사일: 2026-11-15. 요청은 기존 볼륨 구름 질감/빛 반응과 환경을 유지하면서, 제공된 파노라마의 큰 소용돌이와 겹쳐 말리는 형태를 만드는 것이다. 이번 조사에서 Unreal 에셋/레벨은 수정하지 않았다.

## 결론

가능하다. 다만 현재의 관찰 방향 기반 2D 마스크를 기존 밀도 출력에 적용하는 방식만으로는 원하는 3D 말림과 덩어리 배치를 안정적으로 만들기 어렵다. 원래 구름의 노이즈/침식/빛 반응을 유지하는 것과 원래 큰 밀도 분포까지 그대로 유지하는 것은 다르다. 큰 형태를 만드는 밀도 분포와 좌표 변형은 새로 설계해야 한다.

권장 경로는 기존 Volumetric Cloud 렌더러와 셰이딩을 유지하면서, 별도로 저주파 3D 형태 필드(밀도 또는 SDF)를 만들고 그 안에서 기존 구름 노이즈/침식을 사용하는 것이다. 전체 하늘 구현 전에 주 소용돌이 하나로 입체 형태와 질감 양립을 검증한다.

## 확인한 근거

### Epic: 레이아웃, 3D 노이즈, 산란은 분리된 역할

[Volumetric Cloud Material](https://dev.epicgames.com/documentation/en-us/unreal-engine/volumetric-cloud-material-in-unreal-engine)은 Cloud Layout의 위치/마스크/높이 프로파일과 Cloud Shape의 3D 노이즈, Multiscatter를 구분한다. 따라서 기존 질감을 지키기 위해 레이아웃까지 고정할 필요는 없다. 다만 이 문서의 기본 머티리얼이 현재 프로젝트의 사용자 제작 M_07과 동일하다는 뜻은 아니다.

[Volumetric Cloud Component](https://dev.epicgames.com/documentation/en-us/unreal-engine/volumetric-cloud-component-in-unreal-engine)는 Volume Material/Volume Texture 기반 레이 마칭, 다중 산란 근사, 구름 자기 그림자를 설명한다. 원하는 형상은 밀도 필드에 표현해야 한다. 샘플 수 증가는 이미 존재하는 형상을 더 잘 적분하는 용도이며 없는 부피를 만들어 주지 않는다.

### SideFX: 나선 곡선을 실제 구름 부피로 만드는 공식 예제

[Cloud modeling](https://www.sidefx.com/docs/houdini/model/cloud.html)의 Cloud from curve 예제는 Spiral → Cloud Shape from Line → VDB from Particles → Billowy/Wispy Noise 흐름을 제시한다. 즉 소용돌이 곡선을 따라 덩어리를 만들고 노이즈로 구름화하는 제작은 공식적으로 예시된 접근이다. 이것이 Houdini 구매가 필수라는 의미는 아니다. 필요한 것은 곡선에 두께와 층을 가진 3D 부피를 만드는 원리다.

### Guerrilla: 모델링한 부피와 디테일을 분리

[Nubis³, SIGGRAPH 2023 원문](https://advances.realtimerendering.com/s2023/Nubis%20Cubed%20%28Advances%202023%29.pdf)을 내려받아 관련 슬라이드를 검토했다. PDF 페이지 67–79는 모델링/저장, 84–86은 Dimensional Profile과 단면, 118은 프로파일에 노이즈 침식을 적용하는 샘플러, 187은 접근법 비교를 다룬다. 메타볼, 복셀화 메시, 입자, 유체 시뮬레이션 등으로 큰 부피를 만들 수 있다. 프로파일과 노이즈 합성을 분리하는 구조가 이번 요구와 잘 맞는다.

이는 Decima의 제작/렌더링 사례이며 해당 성능이나 모든 기능을 UE 5.8에 그대로 적용할 수 있다는 증거는 아니다. PDF 84/118페이지는 이미지로도 확인했다. 로컬 원문과 추출 결과는 `Saved/SwirlClouds/Research/`에 있다.

### 흐름과 형태는 별개

[Bridson 외, Curl-Noise for Procedural Fluid Flow](https://www.cs.ubc.ca/~rbridson/docs/bridson-siggraph2007-curlnoise.pdf)는 난류를 닮은 비압축성 속도장을 절차적으로 생성하는 방법이다. Curl noise는 움직임/세부 변형에 적합하지만 특정 참조의 소용돌이 위치와 단면을 저절로 만드는 도구는 아니다. 이번에는 큰 형태를 먼저 설계하고 제한된 변형을 적용하는 쪽이 합리적이다. 완전한 유체 시뮬레이션은 필수가 아니다.

## 현재 구현에 대한 진단

직접 읽은 `Saved/SwirlClouds/native_shape_mask.hlsl`은 World에서 고정 중심을 뺀 방향을 정규화해 파노라마 UV를 만들고, mip 3의 밝기를 커버리지로 사용한다. 같은 관찰 광선에서는 거리가 달라도 동일한 커버리지를 가진다. 구름층을 통과하는 방향별 마스크로는 유효하지만, 이것만으로 독립적인 두께/말림/겹침을 정의하지 못한다.

현재 밀도 처리식은 다음과 같다.

`rho = max(0, rho_original - (1-C) * density_scale * 0.35) * C`

C가 0~1이고 density_scale이 양수이면 결과는 원래 양의 밀도보다 클 수 없다. 즉 기존에 없던 덩어리를 추가하거나, 다른 위치로 옮기거나, 두꺼운 말린 단면을 새로 만들 수 없다. 이는 코드를 직접 확인한 구조적 한계다.

반대로 이전 구현은 원본 이미지의 명암을 높이와 경계 albedo에 연결했다. 원본 이미지의 그림자/조명을 실제 형상이나 광학 특성으로 해석해 기존 구름 느낌을 바꿨다. 단일 이미지에는 깊이가 확정되어 있지 않으며, 어두운 부분이 빈 공간인지 그림자인지 반드시 구분되지 않는다.

따라서 두 극단을 피해야 한다.

1. 기존 밀도를 마지막에 잘라 내기만 해서 형태를 만드는 방법.
2. 이미지 명암을 높이/색/산란으로 직접 옮겨 구름을 그림처럼 만드는 방법.

이번의 139개 원본 노드 보존 확인은 원본 동작 보존의 증거이지, 새로운 형태 제작에 성공했다는 증거는 아니다. 이전 결과 보고에서 이 둘을 충분히 구분하지 못했다.

## 방식 비교: 이번 작업 기준의 판단

| 방식 | 장점 | 이 레퍼런스에 대한 한계/용도 |
|---|---|---|
| 기존 밀도에 2D 파노라마 마스크 | 저비용, 기존 질감 유지 용이 | 주로 구름을 제거함. 말린 3D 층의 구성에는 부족 |
| 2D 레이아웃 + 여러 높이 프로파일 + 좌표 변형 | 넓은 하늘의 분포와 흐름을 제어하기 좋음 | 얕은 소용돌이에는 가능. 같은 XY에서 여러 층이 겹치는 깊은 말림은 까다로움 |
| 3D 형태 필드 + 기존 노이즈/침식 + 기존 Cloud 렌더러 | 큰 부피와 세부 질감을 따로 제어 | 권장. 형태 필드 제작/베이크와 해상도 설계가 필요 |
| VDB/SVT와 Heterogeneous Volume | 독립적인 복잡한 부피를 직접 제작 가능 | 별도 렌더링 경로의 빛 반응·비용 검증 필요. 현 단계 기본 선택은 아님 |

2D weather map을 쓰는 모든 구름 방식이 평면이라는 뜻은 아니다. 2D 레이아웃에 3D 노이즈와 높이 구조를 결합하면 실제 볼륨 구름이 된다. 지금 문제가 되는 것은 현재의 최종 출력 마스크만으로 원하는 새 3D 배치를 만들려는 제한된 접근이다.

## 권장 구현 설계

### 유지할 것

- 현재 레벨의 태양/하늘/안개/노출.
- 기존 구름의 albedo, phase function, 다중 산란, 기본 광학 반응.
- 기존 Shape/Erosion 텍스처와 자연스러운 입자·덩어리의 세부 표현을 만드는 원리.

### 교체할 것

- 기존 큰 밀도 분포와 단일 스톰 중심에 종속된 형태 제어 부분.
- 파노라마 명암을 최종 밀도에 곱하는 것에만 의존하는 형태 제작.

### 새 형태 필드

1. 원본을 정면의 색 그림이 아니라 360도 구도의 참조로 사용한다. 투영 규격은 제공되지 않았으므로 현재 360x90 가정부터 검토한다.
2. 주 소용돌이의 중심선과 구름층 경계를 정하고, 폭과 두께가 변하는 3D 띠/타원체 덩어리를 배치한다. 일정한 원형 튜브를 반복해 도넛처럼 보이지 않게 한다.
3. 윗부분이 안쪽으로 넘어가는 단면, 내부 빈 공간, 앞뒤 겹침을 실제 3D로 만든다. 최종 표면 메시를 렌더링하는 것이 아니라 밀도 필드 제작에 사용한다.
4. 이 부피를 저주파 밀도 또는 SDF(경계까지의 부호 있는 거리)로 저장한다. 별도 영역별 볼륨 텍스처로 나누면 전체 하늘을 고해상도 한 덩어리로 저장하지 않아도 된다.
5. 형태 내부에는 기존 구름 노이즈를 채우고, 가장자리에는 기존 침식을 적용한다. 흐름에 맞춘 노이즈 좌표 변형은 제한적으로 사용하여 무작위 결이 큰 흐름을 깨지 않게 한다.
6. 기존 Volumetric Cloud/BSDF 경로로 렌더링한다.

형태 데이터는 노이즈를 담는 빈 틀이 아니라 밀도의 저주파 기반이어야 한다. 기존 완성 밀도와 단순 곱셈만 하면 원래 비어 있던 곳을 여전히 채울 수 없다. 새 큰 밀도에서 기존 노이즈로 덩어리를 분해하는 구조가 필요하다.

Houdini, Blender 또는 절차적 곡선/SDF 생성은 형태 제작 도구의 선택지다. 현재 프로젝트 C++를 추가하기 전에 에셋/머티리얼 경로를 우선 검증한다. 설치된 UE 5.8의 `VolumeTexture.h`에서 Source2DTexture, Source2DTileSizeX/Y, UpdateSourceFromSourceTexture를 확인했지만, 이번 조사에서 새 형태 텍스처 생성/임포트를 실행한 것은 아니다.

## VDB/SVT에 대한 주의 깊은 구분

[Epic Heterogeneous Volumes](https://dev.epicgames.com/documentation/en-us/unreal-engine/heterogeneous-volumes-in-unreal-engine) 및 [Sparse Volume Textures](https://dev.epicgames.com/documentation/en-us/unreal-engine/sparse-volume-textures-in-unreal-engine)는 VDB 임포트와 SVT의 볼륨 머티리얼 활용을 설명한다. SVT는 데이터 표현이고 Heterogeneous Volume은 이를 렌더링하는 액터/경로이므로 같은 개념이 아니다. 문서는 Volumetric Clouds와의 활용도 언급한다.

따라서 VDB를 쓰려면 무조건 기존 Cloud 렌더러를 버려야 한다고 단정할 수 없다. 다만 현재 프로젝트의 Substrate/UE 5.8.4 조합에서 정확히 어떤 경로가 동작하는지는 별도의 작은 검증이 필요하다. 처음부터 이 경로로 이관하기보다 일반 Volume Texture 기반의 형태 필드를 기존 Cloud 재질에서 읽는 방식부터 검토하는 것을 추천한다.

## 형태/광학/렌더 품질을 별도로 검증

원래 albedo/phase/산란과 환경을 유지해도 구름 두께와 겹침이 바뀌면 광학적 경로 길이와 자기 그림자가 달라져 픽셀 밝기는 변한다. 기존 빛 반응을 보존한다는 요구는 물리적 반응과 전체 분위기를 유지한다는 뜻으로 다뤄야 하며, 이전 모든 픽셀 밝기를 유지한다는 뜻은 아니다.

화면의 격자/점 패턴은 별도 문제다. 설치된 5.8 Renderer의 `VolumetricRenderTarget.cpp`에는 quarter/half/full-resolution 추적 및 재구성 모드가 있다. 하지만 이것이 현재 패턴의 확정 원인이라는 증거는 없다. 카메라/시간을 고정하고 시간 누적, 해상도, 샘플 수를 각각 바꾸는 A/B 검증이 필요하다. 형태 설계를 이 문제와 섞어 재질값으로 보정하지 않는다.

## 다음 작업의 완료 기준 제안

전체 하늘 대신 주요 소용돌이 하나로 시작한다.

1. 디테일 노이즈 없이도 말려 들어가는 두께와 겹침이 읽힐 것.
2. 노이즈를 추가해도 실루엣과 내부 빈 공간이 유지될 것.
3. 기존 환경/광학 설정에서 기존 구름과 비슷한 질감이 날 것.
4. 고정 시점 외에 인접한 시점에서도 종이처럼 무너지지 않을 것.
5. 정지/이동 화면의 샘플링 문제를 별도 확인하고 GPU 비용을 측정할 것.

이 검증을 통과한 뒤 파노라마 전체로 확장한다. 특정 프레임 시간, 작업 시간, 최종 유사도는 아직 측정/검증하지 않았으므로 보장하지 않는다.

## 조사 범위와 버전

공식 문서, 제작사 기술 발표, 원 논문 및 현재 로컬 코드/설치된 엔진 소스를 사용했다. 온라인 Epic 페이지는 열람 시 5.9로 표시되었고 5.8 고정 URL은 도구에서 열리지 않았다. 따라서 최신 문서의 SVT 기능을 프로젝트 5.8.4에서 검증 완료했다고 취급하지 않았다. 일반적인 Volume Cloud/Volume Texture 구성과 렌더 타깃 모드는 로컬 5.8 소스에서도 확인했다. 이번 조사에는 새 구현, 렌더 성능 측정, 패키지 테스트가 포함되지 않는다.
